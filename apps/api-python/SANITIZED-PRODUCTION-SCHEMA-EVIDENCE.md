## 2. Parity against the Python backend's expected schema

Comparison target: `apps/api-python/tests/postgres_test_schema.sql`
(base schema) plus `migrations/001..003`.

| Check | Production | Python base schema | Verdict |
|---|---|---|---|
| `users` columns, types, defaults, nullability | 14 columns as listed above | identical 14 columns | **MATCH** |
| `users` UNIQUE(email), UNIQUE(phone), PK | present | present | **MATCH** |
| `data_plans` 17 columns + UNIQUE(network, plan) | as listed above | identical | **MATCH** |
| `transactions` 8 columns + FK(user_id) | as listed above | identical | **MATCH** |
| `sessions` sid/sess/expire + expire index | as listed above | identical | **MATCH** |
| Migration 001 (`api_rate_limits` table) | **absent** | applied by Python at cutover | CORRECTLY NOT APPLIED |
| Migration 002 (catalog + sync columns) | **absent** | applied by Python at cutover | CORRECTLY NOT APPLIED |
| Migration 003 (`uq_users_reset_token_hash` partial unique index) | **absent** | applied by Python at cutover | CORRECTLY NOT APPLIED |

**Intentional, harmless differences:** production `users`/`transactions`
use `DEFAULT nextval(...)` (serial) while the Python base schema uses
`GENERATED BY DEFAULT AS IDENTITY`. Both assign integers on insert when
no id is given and both accept explicit ids, so the Python backend can
read and write production rows without changes. Production
`data_plans.id` carries no default (Node inserts explicit ids); the
Python schema's identity default is a superset of that behavior.

## 3. Conclusion

The production database is **structurally identical** to the Python
backend's base schema for every application table, and none of the
Python-side migrations (001–003) have been applied to production —
exactly the state required by the migration plan (migrations apply to
production only at cutover, with owner authorization). The only
non-application object is the `playing_with_neon` experimentation table.

This closes the "sanitized production-schema evidence" owner gate.
